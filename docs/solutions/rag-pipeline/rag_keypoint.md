## 决策

chunk_size = 512 tokens, chunk_overlap = 50 tokens（约 10%）。

## 理由

业界默认策略中，512 tokens 被认为是“上下文与精度之间的甜点区”：太小（128–256）会把完整概念切碎，太大（1024–2048）会稀释相关性、浪费 LLM token。50 token 的重叠是为了防止关键句子恰好落在边界上被切断。

本次语料是产品 FAQ 和内部流程文档，平均段落长度在 300–500 token 之间，512 基本能覆盖一个完整的问答对。

## 验证方式

取 20 条已知“问题 → 正确 chunk”的测试样本，用当前配置做检索，记录 top-4 命中率。如果命中率低于预期，下一步会尝试 384 或 768 做对比。

## 阶段2真实验收记录（2026-11-11）

使用 `raw_data/` 下真实政策文档与 65 页冰箱说明书构建知识库，并按
`rag/eval/golden_set.jsonl` 中 19 条可回答政策题计算 Recall@4：

| 配置 | 政策块数 | 说明书块数 | 重复内容块数 | 政策 Recall@4 |
| --- | ---: | ---: | ---: | ---: |
| 500 字符 / 50 overlap | 3 | 614 | 0 | 19/19 = 100% |
| 768 字符 / 50 overlap | 3 | 246 | 0 | 19/19 = 100% |

结论：两种配置在当前政策语料上都达到 100%；政策文档只有 3 个内容块，
top-4 实际覆盖全部政策块，因此该指标已饱和，不能据此证明 768 更优。说明书
在 768 下块数更少且表格块更大，但当前 golden set 没有可回答的说明书题，
无法比较说明书召回。阶段2继续采用 500 字符 / 50 overlap，待阶段4补充
可回答的说明书题后再用真实问答数据比较 500/768。
